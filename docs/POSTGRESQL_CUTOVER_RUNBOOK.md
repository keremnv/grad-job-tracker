# Proposed PostgreSQL cutover runbook — NOT EXECUTED

**AWS target selected:** follow [AWS deployment preparation](../infra/aws/README.md) and [AWS authority handoff](AWS_CUTOVER.md) for the host-specific steps. PostgreSQL uses local peer authentication on EC2 and authenticated SSM tunnels for remote access; the generic direct-host TLS/Actions-secret examples below describe alternatives, not a public database requirement. The selected scheduled writer is systemd, not a second GitHub Actions collector. No hosted environment or cutover is authorized by these documents.

Stage 4A authorizes none of the hosted/deployment steps below. The file-backed production tracker remains authoritative. Execute this only during a separately authorized Stage 4B deployment, with an operator recording outcomes privately. Do not merge or enable the inert workflow just to try it.

## 1. Prepare before migration

1. Provision the selected hosted PostgreSQL 17 environment separately; configure data region, administrative/deployment login, two runtime logins, ownership and least-privilege grants. Use the Stage 1 bootstrap or managed-provider equivalent. Runtime logins must not own the schema or inherit the deployment role. No provider or account is assumed provisioned by this repository.
2. Configure authenticated libpq service/passfile or approved secret-manager settings **outside Git**. Test certificate/hostname verification (`sslmode=verify-full`), database identity and distinct owner/collector/deployment sessions. Do not echo full DSNs or passwords in logs. `JOBWATCH_MIGRATION_DATABASE_URL` never falls back to runtime credentials. Inspect `pg_stat_ssl` for the current backend and run permission/denial checks as the real runtime logins.
3. Apply the exact packaged migration checksums explicitly. Test restore into a **separate fresh database in the actual hosting environment**, with roles provisioned first. Use real `pg_dump`/`pg_restore`, verify data/history/owner state, schema/ownership/grants/migration ledger, sequences, all views and useful SQL queries. Local Stage 3/4A proof does not establish hosted PITR/backup retention. Configure operational backup access/retention and test the actual selected recovery mechanism; keep owner data private.
4. Rehearse the importer at a current frozen commit on a non-authoritative target, then the SQL-backed daily/weekly/requirements/calendar reports, both search methods, owner workflow and source health. Review the functionality matrix. Confirm SQL-first agent instructions/read tools and every operational report needed by the owner; old CLI wrappers are not a mandatory compatibility target.
5. Complete genuine endpoint checks for all nine intended ATS sources on the rehearsal target, inspect employer-association evidence separately, and record exact source identity/contract/check receipt/provenance. Do not claim that old mapping dates are endpoint checks. A fixture is never acceptable real check evidence. If final configuration changes, revalidate the affected endpoint/mapping. The final import must remain empty-target; do not preseed it with these rehearsal runs. After import, use fresh real checks (the simplest path) or deliberately carry the real dated facts with reviewed ordinary SQL tied to the final identities, never invented current timestamps.
6. Obtain explicit owner acceptance of the two historical limits: current schema-2 native responses were not archived, and rejected roles never indexed before schema 2 have unknown identities/counts. There are no unresolved recorded description hashes in the 90434ea rehearsal, but the **final** source must be reconciled independently. Record any newly unavailable reference or unsupported field; do not hide it in a passing count.
7. Prepare the collector-only GitHub Actions secret, TLS/service settings, permissions and proposed workflow without enabling it. Keep migration and owner credentials out of the collector job. The inert template removes observation commits/push/rebase and contents-write permission. It emits a public source-only summary, not private weekly/owner reports.
8. Agree a freeze window with the owner. Stop the active file schedule, wait for in-flight runs/retries to finish, and stop owner ledger/triage/verification/configuration writes. Commit/push legitimate pending owner edits through the existing authorized workflow first. Do not reset/discard a dirty checkout. The freeze covers all authoritative input files, not just jobs.json.

## 2. Freeze the real final source, then import once

1. Fetch/read the current production branch in a clean, complete local repository. Resolve the actual authoritative commit **C** and verify local/remote SHA equality. **Do not blindly reuse `90434ea6d9a3457f9c8ba40f01ad25fa2ceffca3`**; that is an old rehearsal input. Confirm no workflow or owner write advanced main after the freeze.
2. Preserve a pre-cutover Git tag/snapshot/bundle for C, including the historical objects required by the importer. Keep private owner input private. Record the exact commit and source file hashes; Git commit time is not an employer edit time.
3. Prepare a fresh target with approved migrations/roles. Use `jobwatch-pg-import plan --repo ... --commit C --report PRIVATE_NEW_FILE`; review key sets, dates, evidence recovery, owner data, source identities, extra fields, limitations and activation gates. A wrong hash, ambiguous identity or unsupported structure fails before authoritative import. Fix the plan/input question deliberately; do not relax tests or fabricate source facts.
4. `jobwatch-pg-import import` C once with deployment credentials, followed by independent `reconcile` C. Require all exact row/field/payload/reference checks, owner/audit images, distributions and source health chronology. A populated target is refused; never delete/truncate it to resolve an uncertain outcome. After lost COMMIT acknowledgment, reconnect and reconcile to determine whether the import committed.
5. Take a real backup of this reconciled baseline, restore it separately and reconcile the restored database against C and the imported baseline. Save safe reconciliation/restore receipts. Run baseline readiness with those receipts; review every failed local check and external requirement.
6. Establish final source endpoint/mapping facts and activate through audited owner SQL/the helper. Verify provider/board/region, actual check run/receipt and original enabled configuration. Candidates must not be silently treated as successful monitored sources; no source expansion or reduction without an explicit owner coverage decision. Validate without publishing postings while still staging.
7. Take a verified **pre-promotion backup including the activation facts**. Verify owner/application/triage/lead/verification hashes, all imported immutable evidence and source pointers. Run operational readiness: mutable changes from explicit activation must not invalidate old immutable history, while old baseline receipts must not be described as current whole-DB equivalence. Persist all receipts privately. If an input moved during the freeze, stop and select a new C; there is no dual-write catch-up importer.

## 3. Switch the single authority

1. Deploy the tested PostgreSQL code and SQL read/report instructions together. Explicitly retire/disable active JSON/CSV/text writers, mutable-file defaults and redundant file-backed read wrappers at this point, including owner commands that would otherwise write stale files. Preserve historical Git objects, not an active parallel datastore. Stage 4A has deliberately not deleted those writers yet.
2. Replace the existing file-backed workflow, using the reviewed inert template as the proposed replacement. Confirm the old job is disabled/stopped before the new one can run. Scheduling/concurrency grouping is convenience; source-row transaction ordering remains correctness. Do not run both writers or add ongoing file-to-PostgreSQL synchronization.
3. Confirm the workflow's actual database/role/environment without displaying credentials. Use collector credentials only; no schema migration/import on startup, no owner ledger queries, no git observation commits and no push token. Normal SQL owner/research access remains available through standard tools.
4. Keep ordinary scheduling paused while doing the first controlled new collection. Confirm the explicit authority/promotion time and preserve the pre-promotion backup. Code rollback alone is no longer a safe data rollback after new DB writes.

## 4. Verify after switching

1. Execute one controlled `jobwatch-pg-ops scan --actor ...`. Nonzero status does not undo other source commits. Inspect each registered run UUID/order, actual terminal outcome, receipt, counts and source pointer. Skips/supersession are not successes; unknown outcomes require SQL inspection/recovery. All-failed and partially failed sources must retain prior observations.
2. Inspect new immutable native versions and baseline events on legacy-only current records. Confirm source response versus normalizer/screening/observation attribution; no fabricated employer edit times. Replay one known result safely where appropriate; do not refetch under its UUID. Excluded postings remain recorded.
3. Verify Lever multi-page publication is positive-only. Previously listed unreturned records retain status/last-positive time and are visibly `retained_after_positive_only_run`; no false absence events. A valid complete empty board is a successful zero-vacancy scan; a malformed/partial board cannot close anything. `not_seen` never verifies an application form is closed.
4. Compare owner application/triage/lead/verification fields and private hashes with the pre-scan snapshot. No collector update may change them. Check audit attribution, application/triage precedence, manual keys and exact versus ambiguous URL links.
5. Exercise broad research, historical/native evidence, material queries, attention queue, deadline uncertainty, programme cycles, weekly/requirements/calendar rendering, BM25 and FTS. Confirm notes/CV labels/credentials do not enter automated summaries. Verify stdout JSON/summary exit handling in the real job environment.
6. Review actual health/coverage, processing revision, SQL role denials, backups and operational readiness. Resume ordinary scheduling only after all required outcomes are confirmed. Keep source/provider problems explicit rather than masking them as successful collection.

## 5. Recovery boundaries

**Before promotion and before new authoritative PostgreSQL observations/owner writes:** keep the frozen file snapshot C authoritative, preserve candidate evidence/checks/receipts, stop the candidate workflow and discard/repair only the non-authoritative database after diagnosing the issue. Re-enable the old writer deliberately from C only after confirming no later authoritative data would be lost. Staging endpoint facts may be preserved or genuinely rechecked; do not backdate replacement checks.

**After promotion or any committed authoritative DB change:** stop scheduled and owner writers; take a fresh recoverable backup of the current DB before repairs. Do **not** restart the frozen Git writer at C. That loses later source evidence and owner decisions. Restore to a **separate** database, verify schema/roles/grants/ledger/sequences, reconcile imported immutable history and all valid later observations/owner changes, and repair/roll forward or promote the independently verified target. Retain the pre-repair DB/backup until recovery is accepted.

For a source publication problem, prefer Stage 2 idempotent/run-order recovery or a new genuinely fetched run, not table rewrites/deleting evidence. For mutable owner mistakes, inspect the narrow private audit and make an attributed compensating correction. Do not recreate Git or implement generalized event replay/reverse synchronization. A hosted PITR choice is an operator recovery action with its own later-write reconciliation, not permission to overwrite valid subsequent owner records.

The operator records the final commit, authority time, checks, accepted limitations, actual-host restore proof, source activation evidence, backup IDs and go/no-go decision privately. The Stage 4A readiness command lists external gates but cannot authorize or attest these hosting/owner actions.
